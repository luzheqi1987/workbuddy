## 一、背景与目标

### 1.1 背景

我司电商平台日均承接用户咨询量约 **120 万次**，其中智能客服（机器人）承接占比 **68%**，人工客服承接占比 **32%**。当前智能客服基于**规则引擎 + 意图分类器**架构，通过预配置的话术模板和关键词匹配进行自动回复。

随着业务复杂度提升，规则引擎的局限性日益突出：

- 规则库已膨胀至 **12,000+ 条**，维护成本高，冲突频发
- 用户意图识别准确率从上线初期的 **89%** 下降至 **71%**
- 复杂问题转人工率达 **42%**，远超行业 **25%** 的平均水平
- 用户满意度（CSAT）从 **4.2** 降至 **3.5**（满分 5 分）

### 1.2 问题根因

经数据分析，转人工的会话中 **76%** 属于以下三类场景：

| 场景类型 | 占比 | 典型案例 | 规则引擎为何无法处理 |
|----------|------|----------|----------------------|
| 多意图混合 | 38% | "我上周买的蓝色杯子收到有缺口，想换绿色的，顺便问下退货流程" | 一条消息同时包含售后换货 + 颜色变更 + 政策咨询三个意图 |
| 上下文关联 | 24% | 用户先问"发货了吗"，紧接着说"那改个地址吧，之前的填错了" | 第二句话需要结合第一句话的订单上下文才能理解 |
| 开放式问题 | 14% | "这个面膜敏感肌能用吗？我之前用别的牌子会泛红" | 依赖商品知识 + 用户画像 + 医学常识的综合推理 |

### 1.3 目标

引入大语言模型（LLM）重构智能客服核心引擎，实现：

| 指标 | 当前值 | 目标值 | 衡量方式 |
|------|--------|--------|----------|
| 意图识别准确率 | 71% | ≥90% | 抽样标注评测 |
| 复杂问题转人工率 | 42% | ≤22% | 系统统计 |
| 用户满意度（CSAT） | 3.5 | ≥4.3 | 会话结束评分 |
| 平均响应时间 | 1.2s | ≤3.0s | 端到端延迟 |
| 规则维护人力 | 6人 | 2人 | 团队编制 |

## 二、现状分析

### 2.1 现有架构

```
用户消息 → 关键词预处理 → 意图分类器（FastText）→ 规则匹配引擎 → 模板回复
                                                      ↓
                                                   未命中 → 转人工
```

### 2.2 核心缺陷

#### 缺陷 1：单意图假设失效

现有意图分类器基于单标签分类，假设每条用户消息只包含一个意图。但实际数据表明，**31%** 的用户消息包含 2 个及以上意图。当多意图消息进入系统时：

- 分类器只取 top-1 意图，其余意图被丢弃
- 用户只收到部分回复，需要反复追问
- 典型案例：用户说"退货并退款"，系统只识别为"退款咨询"，给出退款流程，但未处理退货物流

#### 缺陷 2：无上下文记忆能力

规则引擎以单条消息为处理单元，不维护会话状态。导致：

- 代词指代无法解析（"那个"、"它"、"刚才说的"）
- 省略句无法补全（用户说"换个S码的"，系统不知道换什么商品）
- 多轮交互中用户修正信息无法更新（用户先说收货地址A，后说"还是寄到B吧"）

#### 缺陷 3：知识覆盖刚性

商品知识库和FAQ采用结构化存储，只能回答精确匹配的问题。对于：

- 需要跨商品比较的问题（"这两款精华哪个更适合油皮"）
- 需要推理的问题（"我孕期可以用这个成分的护肤品吗"）
- 需要结合用户历史的问题（"上次买的那个再推荐个类似的"）

规则引擎完全无法处理，全部转人工。

#### 缺陷 4：话术生硬，缺乏个性化

模板回复内容固定，无法根据用户语气、情绪、历史偏好调整沟通风格。用户反馈"像跟机器人说话"、"回答千篇一律"。

## 三、解决方案概述

### 3.1 核心思路

引入大语言模型作为智能客服的"大脑"，构建 **"LLM 推理 + 工具调用 + 知识增强"** 三层架构：

```
用户消息
    │
    ▼
┌─────────────────────────────────────┐
│         LLM 推理引擎                │
│  · 多意图识别与拆解                  │
│  · 上下文理解与会话状态维护           │
│  · 开放式问题推理                    │
│  · 个性化话术生成                    │
└──────────┬──────────────────────────┘
           │
    ┌──────┴──────┐
    ▼             ▼
┌────────┐   ┌──────────┐
│ 工具层  │   │ 知识层    │
│ 订单查询 │   │ 商品库    │
│ 物流查询 │   │ FAQ库     │
│ 售后创建 │   │ 政策文档  │
│ 库存查询 │   │ 用户画像  │
└────────┘   └──────────┘
    │
    ▼
  回复用户
```

### 3.2 关键设计决策

| 决策点 | 方案 | 理由 |
|--------|------|------|
| 模型选择 | 自研 7B 模型 + 通用大模型双路 | 高频简单问题走 7B（低延迟、低成本），复杂问题走通用大模型（高能力） |
| 路由策略 | 轻量分类器预判复杂度 | 避免 all-LLM 带来的延迟和成本问题 |
| 知识增强 | RAG（检索增强生成） | 避免幻觉，保证回答有据可依 |
| 安全兜底 | 敏感意图检测 + 人工兜底阈值 | 确保大模型不输出违规内容，不确定时转人工 |

## 四、详细功能需求

### 4.1 多意图识别与并行处理

**需求描述**

系统需支持从单条用户消息中识别多个意图，并分别生成对应的处理方案，最终合并为一条连贯的回复。

**功能规则**

| 规则编号 | 规则描述 | 优先级 |
|----------|----------|--------|
| F1.1 | 支持识别单条消息中最多 5 个并行意图 | P0 |
| F1.2 | 对每个识别出的意图，独立调用对应工具或知识检索 | P0 |
| F1.3 | 合并多个意图的回复时，需保证逻辑连贯、不重复 | P0 |
| F1.4 | 当多个意图存在冲突（如"退货"且"确认收货"）时，需向用户澄清 | P1 |
| F1.5 | 输出意图识别置信度，低于阈值（0.6）时转人工 | P0 |

**输入/输出示例**

```
用户消息："我上周买的蓝色杯子收到有缺口，想换绿色的，顺便问下退货流程"

系统识别：
  - 意图1：售后换货（商品：蓝色杯子，问题：缺口，目标：换绿色）
  - 意图2：退货政策咨询

系统回复：
  "很抱歉您收到的杯子有缺口！我马上帮您处理换货：
   1. 已为您创建换货申请，新商品为绿色同款，无需补差价
   2. 请将原商品寄回，运费由我们承担，退货物流单号已发您短信

   关于退货流程：自签收起7天内可申请退货，商品需保持完好。
   如您还有其他问题，随时告诉我~"
```

### 4.2 多轮上下文理解与会话状态管理

**需求描述**

系统需维护完整的会话状态，支持跨轮次的上下文引用、指代消解和信息修正。

**功能规则**

| 规则编号 | 规则描述 | 优先级 |
|----------|----------|--------|
| F2.1 | 维护会话级状态对象，包含：当前讨论商品、订单号、用户诉求、已提供信息 | P0 |
| F2.2 | 支持代词指代消解（"那个"、"它"、"刚才说的"→ 具体实体） | P0 |
| F2.3 | 支持省略句补全（根据上下文推断被省略的主语/宾语） | P0 |
| F2.4 | 支持用户信息修正（用户更改之前提供的地址、颜色等） | P0 |
| F2.5 | 会话上下文窗口：最近 10 轮对话 | P1 |
| F2.6 | 超过 30 分钟无交互的会话，上下文失效，需重新初始化 | P1 |

**会话状态数据结构**

```json
{
  "session_id": "S20260720001",
  "user_id": "U123456",
  "topic": "售后换货",
  "entities": {
    "order_id": "DD20260715001",
    "product": "陶瓷马克杯",
    "variant": { "color": "蓝色", "size": "350ml" },
    "issue": "缺口",
    "desired_variant": { "color": "绿色" }
  },
  "pending_actions": ["create_exchange"],
  "resolved_intents": ["售后换货", "退货政策咨询"],
  "turn_count": 4,
  "last_active": "2026-07-20T14:30:00Z"
}
```

### 4.3 RAG 知识增强问答

**需求描述**

对于商品咨询、政策问答等需要外部知识的场景，系统通过 RAG 检索相关文档，将检索结果作为上下文输入 LLM，生成准确且有依据的回答。

**功能规则**

| 规则编号 | 规则描述 | 优先级 |
|----------|----------|--------|
| F3.1 | 知识源覆盖：商品库（50万SKU）、售后政策（120篇）、FAQ库（8000条） | P0 |
| F3.2 | 检索策略：混合检索（向量相似度 + BM25关键词），Top-K=5 | P0 |
| F3.3 | LLM 生成回答时，必须基于检索结果，不得编造不存在的信息 | P0 |
| F3.4 | 回答需附带信息来源引用（如"根据《七天无理由退货政策》第3条..."） | P1 |
| F3.5 | 当检索结果为空或相关度低于阈值时，明确告知用户并转人工 | P0 |
| F3.6 | 商品比较类问题，需结构化对比（价格、规格、适用人群等维度） | P1 |

### 4.4 工具调用与业务执行

**需求描述**

LLM 需具备工具调用（Function Calling）能力，可根据用户意图自动调用后端业务接口，执行订单查询、售后创建等操作。

**工具清单**

| 工具名称 | 功能 | 输入参数 | 输出 | 优先级 |
|----------|------|----------|------|--------|
| query_order | 查询用户订单 | user_id, order_id(可选) | 订单详情列表 | P0 |
| query_logistics | 查询物流状态 | order_id | 物流轨迹 + 预计送达 | P0 |
| create_return | 创建退货申请 | order_id, reason, item_list | 退货单号 | P0 |
| create_exchange | 创建换货申请 | order_id, reason, new_variant | 换货单号 | P0 |
| query_inventory | 查询库存 | sku_id | 可用库存 + 预计补货时间 | P1 |
| query_coupon | 查询用户优惠券 | user_id | 有效优惠券列表 | P2 |
| modify_address | 修改收货地址 | order_id, new_address | 修改结果 | P1 |

**调用规则**

| 规则编号 | 规则描述 | 优先级 |
|----------|----------|--------|
| F4.1 | LLM 一次对话最多调用 3 个工具，避免过长等待 | P0 |
| F4.2 | 涉及资金类操作（退款、赔偿）必须用户二次确认 | P0 |
| F4.3 | 工具调用失败时，LLM 需给出友好提示并记录错误日志 | P0 |
| F4.4 | 工具调用结果需 LLM 转化为自然语言回复，不得直接返回 JSON | P0 |

### 4.5 情绪感知与个性化话术

**需求描述**

系统需识别用户情绪状态，并据此调整回复的语气、emoji 使用和安抚策略，提升用户体验。

**功能规则**

| 规则编号 | 规则描述 | 优先级 |
|----------|----------|--------|
| F5.1 | 情绪识别维度：正面/中性/负面，负面细分：不满、愤怒、焦虑 | P0 |
| F5.2 | 负面情绪会话优先分配高级模型，并推送质检标记 | P0 |
| F5.3 | 连续 2 轮负面情绪自动触发人工介入兜底 | P0 |
| F5.4 | 根据用户历史偏好调整话术风格（简洁型/详细型/亲切型） | P2 |
| F5.5 | 话术风格需与品牌调性一致，禁止过度使用网络用语 | P1 |

### 4.6 安全与兜底机制

**需求描述**

确保大模型输出内容安全合规，在不确定或高风险场景下能正确兜底。

**功能规则**

| 规则编号 | 规则描述 | 优先级 |
|----------|----------|--------|
| F6.1 | 输入安全过滤：检测并拦截 prompt injection、政治敏感、涉黄涉暴内容 | P0 |
| F6.2 | 输出安全过滤：检测并拦截违规回复，替换为安全兜底话术 | P0 |
| F6.3 | 置信度兜底：LLM 回复置信度 < 0.6 时，转人工处理 | P0 |
| F6.4 | 频次兜底：同一用户 10 分钟内转人工超 3 次，直接接入人工 | P0 |
| F6.5 | 所有 LLM 生成内容需记录完整日志（输入、输出、工具调用、模型版本） | P0 |
| F6.6 | 支持人工质检抽检，抽检比例 ≥5%，覆盖各场景类型 | P1 |

## 五、非功能需求

### 5.1 性能需求

| 指标 | 要求 | 说明 |
|------|------|------|
| 端到端响应延迟 | P50 ≤ 2.0s，P95 ≤ 5.0s，P99 ≤ 8.0s | 含 LLM 推理 + 工具调用 + 知识检索 |
| 系统吞吐 | 峰值 QPS ≥ 3000 | 大促期间峰值预估 |
| 可用性 | SLA ≥ 99.95% | 月度可用率 |
| 降级能力 | LLM 不可用时 3s 内降级至规则引擎 | 保证业务连续性 |

### 5.2 安全合规需求

| 需求 | 说明 |
|------|------|
| 数据脱敏 | 用户 PII（手机号、地址、身份证）在输入 LLM 前脱敏 |
| 模型隔离 | LLM 推理在私有环境部署，数据不出内网 |
| 审计日志 | 全链路日志留存 90 天，支持审计追溯 |
| 内容合规 | 回复内容需符合《广告法》《电商法》等法规要求 |

### 5.3 可观测性需求

| 指标 | 说明 |
|------|------|
| 实时监控大屏 | 展示 QPS、延迟分布、意图识别准确率、转人工率、CSAT |
| 告警 | 延迟 P95 > 5s、错误率 > 1%、转人工率 > 30% 时自动告警 |
| 离线分析 | 支持按场景、模型版本、时间段进行离线效果分析 |

## 六、用户场景与用例

### 场景 1：多意图售后处理

```
用户：我昨天收到的那个蓝牙耳机左耳没声音，想换一个，但是要黑色的，蓝色没货就算了
```

**系统处理流程：**

1. LLM 识别意图：售后换货 + 库存咨询
2. 提取实体：商品=蓝牙耳机，问题=左耳无声，期望=黑色
3. 调用 `query_inventory` 查询黑色款库存 → 有货
4. 调用 `create_exchange` 创建换货单
5. 生成回复

```
系统：抱歉给您带来不好的体验！已为您处理：
     1. 检测到黑色款有库存，已创建换货申请（单号：HH20260720001）
     2. 请将原蓝色耳机寄回，运费我们承担，物流单号已发您短信
     3. 黑色款预计 7月22日 发出

     还有其他需要帮您的吗？
```

### 场景 2：上下文关联的多轮对话

```
Turn 1:
用户：帮我查下最近买的耳机到哪了
系统：您最近购买的是"XX蓝牙耳机"（订单号DD20260718001），目前已在运输中，
     预计明天送达。物流信息：已到达【上海转运中心】，正在派送中。

Turn 2:
用户：那改个地址吧，寄到我公司
系统：好的，请提供您公司的收货地址，我帮您修改。
用户：浦东新区XX路XX号XX大厦15楼
系统：已将订单 DD20260718001 的收货地址修改为：浦东新区XX路XX号XX大厦15楼。
     请注意，因已发出派送，修改地址可能导致配送延迟 1-2 天。

Turn 3:
用户：那个耳机的充电仓是Type-C的吗
系统：是的，这款蓝牙耳机的充电仓采用 Type-C 接口，充电约 2 小时可充满，
     单次续航 6 小时，配合充电仓总续航 24 小时。
```

### 场景 3：开放式商品咨询

```
用户：我敏感肌，之前用烟酰胺会泛红，这个精华液能用吗？
```

**系统处理流程：**

1. LLM 识别：开放式商品咨询，需知识增强
2. RAG 检索：商品成分表 + 敏感肌护肤指南
3. 检索结果：该精华液含 5% 烟酰胺 + 神经酰胺
4. LLM 推理：用户对烟酰胺不耐受 → 该产品含烟酰胺 → 建议谨慎

```
系统：这款精华液含有 5% 浓度的烟酰胺成分，考虑到您之前使用烟酰胺有泛红反应，
     建议您谨慎选择。

     有几个建议供您参考：
     1. 如仍想尝试，建议先在耳后做局部测试，确认无不良反应后再上脸
     2. 这款产品同时含有神经酰胺（修护屏障成分），可能降低刺激性，但不能保证
     3. 如果您想找类似功效但不含烟酰胺的产品，我可以为您推荐

     需要我帮您推荐替代产品吗？
```

## 七、技术方案概要

### 7.1 系统架构

```
                          ┌──────────────────────┐
                          │      用户端           │
                          │  (APP / Web / 小程序)  │
                          └──────────┬───────────┘
                                     │
                          ┌──────────▼───────────┐
                          │    API Gateway       │
                          │   (鉴权 / 限流 / 路由) │
                          └──────────┬───────────┘
                                     │
                    ┌────────────────▼────────────────┐
                    │       智能客服编排层 (Orchestrator) │
                    │  · 复杂度预判路由                   │
                    │  · 会话状态管理                     │
                    │  · 工具调用编排                     │
                    │  · 安全过滤                        │
                    └───────┬──────────────┬───────────┘
                            │              │
               ┌────────────▼──┐    ┌──────▼──────────┐
               │  简单问题快通道  │    │  LLM 推理引擎    │
               │  规则引擎 + FAQ │    │  (通用大模型)    │
               │  延迟 <500ms   │    │  延迟 1-3s      │
               └───────────────┘    └──────┬──────────┘
                                           │
                          ┌────────────────┼────────────────┐
                          │                │                │
                   ┌──────▼──────┐  ┌──────▼──────┐  ┌──────▼──────┐
                   │  RAG 引擎   │  │  工具服务层  │  │  安全过滤层  │
                   │ 向量检索+重排 │  │ 订单/物流/售后│  │ 输入/输出过滤 │
                   └─────────────┘  └─────────────┘  └─────────────┘
```

### 7.2 核心模块说明

| 模块 | 技术选型 | 说明 |
|------|----------|------|
| 复杂度路由 | LightGBM 分类器 | 预判消息复杂度，决定走规则引擎还是 LLM |
| LLM 推理引擎 | 自研7B + 通用大模型双路 | 简单推理走7B，复杂推理走通用大模型 |
| RAG 引擎 | Milvus + BGE-M3 向量模型 | 向量检索 + BM25 混合检索，Cross-Encoder 重排 |
| 会话状态 | Redis（热）+ MySQL（冷） | 10轮窗口内热存储，超时归档冷存储 |
| 工具服务 | gRPC 微服务 | 复用现有业务接口，LLM 通过 Function Calling 调用 |
| 安全过滤 | 关键词 + 小模型分类 | 双重过滤，输入侧防注入，输出侧防违规 |

### 7.3 模型选型对比

| 维度 | 自研7B | 通用大模型 | 备注 |
|------|--------|-----------|------|
| 推理能力 | 中 | 强 | 复杂推理需通用大模型 |
| 响应延迟 | 0.3-0.8s | 1.0-3.0s | 7B 适合高频简单场景 |
| 部署成本 | 高（GPU集群） | 按调用量付费 | 7QPS > 500后自研更经济 |
| 可控性 | 强（可微调） | 弱 | 自研模型可注入领域知识 |
| 数据安全 | 内网部署 | 需评估 | 涉及用户数据优先内网 |

**决策**：双路并行，路由层根据复杂度动态选择。预估 65% 流量走 7B，35% 走通用大模型。

## 九、风险评估与应对

| 风险 | 等级 | 影响 | 应对措施 |
|------|------|------|----------|
| LLM 幻觉导致错误回复 | 高 | 用户投诉、业务损失 | RAG 约束 + 置信度兜底 + 5%质检抽检 |
| 响应延迟超标 | 高 | 用户等待、体验下降 | 双路路由 + 流式输出 + 超时降级规则引擎 |
| Prompt Injection 攻击 | 中 | 系统被操纵、信息泄露 | 输入侧安全过滤 + 模型 System Prompt 加固 |
| 大促流量峰值 | 中 | 系统过载、响应超时 | 通用大模型配额预留 + 自动降级策略 |
| 知识库更新不及时 | 中 | 回复信息过期 | 知识库 T+1 更新机制 + 运营手动热更新通道 |
| 模型版本迭代回归 | 低 | 效果下降 | 模型版本管理 + 上线前回归测试集（500 case） |
