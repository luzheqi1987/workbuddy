## `sys_code` 语义定稿 + 请求头传递规范（用户澄清）
- 用户定性：**`sys_code` = 外部系统调用我们网关时的系统标识**，习惯 4 或 6 位字母，但**不强制格式，允许自定义**
- 因此删掉上一版写的"4/6 位正则硬约束"，改为：不卡格式 + 只做安全清洗（长度 ≤32、字符集 `A-Za-z0-9_-`、拒绝控制字符、比对前统一大写）；但**取值仍须在 Key 上登记**（"不卡格式 ≠ 不登记"，否则可伪造头蹭配额/污染指标）
- 一个 sys_code 可绑多个 Key（轮换期双 Key 并存）→ 不加唯一约束，示例数据补了 `InboundAgentKeyV2`
- 鉴权三步（§7.1）：Key 查权威 sys_code → 与请求头 `X-Sys-Code` 比对（缺失用权威值兜底不报错；不一致默认 401 `SYS_CODE_MISMATCH`，迁移期开关可降级为告警）→ 权威值写 MDC。**头值只用于比对，绝不进限流 key / 授权判定 / 指标标签**
- 新增 §7.5「调用链标识与排查」：入站 `X-Sys-Code`（客户端，不可信）/ 出站 `X-Gateway-Sys-Code`（网关重写）/ `X-Request-Id` / 响应回传 `X-Gateway-Trace-Id`（客户端报障给单号）；`x-sys-code` 进 STRIP_HEADERS（后端只认 `X-Gateway-Sys-Code`，与删 `x-allow-mcp-tools` 同类问题）；正向/反向排查路径各一条
- 连带：§2.2 示例改为 4/6 位码；§2.7/call_log 记权威值；§3.1/§5/§7.1 出站头补 `X-Gateway-Sys-Code`；§7.4-C 明确只取权威值；§10 新增"入站请求头一律不可信"风险条；M5 里程碑补头规范
- 用户偏好：**不要过度约束格式**（4/6 位是习惯而非规则），但要保住可排查性与不可伪造
- 用户明确指出我写的「`INBOUND` ✅」条件式必填是多余的：**必填就是必填**，两个方向都填 `sys_code`，含义由 `direction` 决定（INBOUND=调用方系统码，OUTBOUND=后端系统码）。SQL 改回 `NOT NULL`；文档表述统一去掉条件式写法

## 授权模型重构：废弃动态头，改为库里的调用方授权（用户质疑「动态头里有就有权限」不合理）
- 用户定性：**不同系统的工具权限必须由我（管理员）授予**，不是请求头里声明什么就有什么。动态头 = 调用方自授权，且鉴权插件漏配就全开
- 新增第 5 张表 **`mcp_gw_grant`**（sys_code × service_name × subject 唯一）：`allow_tools`（原始工具名，null=该服务全部，[]=不放开）、`effect`(ALLOW/DENY，DENY 优先)、`status`、`expire_at`；随注册表一起进 Caffeine 缓存，**授权变更必须走主动失效链路**（否则紧急封禁要等 30s）
- `mcp_gw_auth_scheme` 加 `subject` 列（默认 `*`）：同一系统不同角色/租户/套餐发不同 Key，**角色由 Key 登记而非请求头声明**，用于匹配 grant.subject
- 判定模型（§2.6）：**服务侧工具上限 `allow_tools` ∩ 调用方授权 `mcp_gw_grant` = 生效工具集**；无授权行 = 全禁（fail-closed，全局开关 `grant.default-mode` 默认 DENY，迁移期可 ALLOW 但上线前收回）
- 语义不对称要保留：服务 allow_tools null = 全允许；授权行不存在 = 全禁
- 五条强制规则：list/call 共用 `granted()`；无授权行 fail-closed；原始工具名匹配；**请求头不参与授权判定**（`x-allow-mcp-tools` 不采信，入站丢弃）；判定只认 Key 解析的 sys_code 权威值
- 连带修订：§2.0 模型图/层表、§2.1 allow_tools 改称"服务侧工具上限"、§2.2 加 subject 列、§3.1/§3.3 代码（`granted(svc, rawTool, caller)`）、§6 聚合入口改传 `Caller`、§5.1 STRIP_HEADERS、§7.1 第 3 步不再写头、§7.4 deny_reason 枚举化（NOT_GRANTED / NOT_IN_SERVICE_ALLOWLIST / RATE_LIMITED / EGRESS_DENIED / AUTH_FAILED）、§8 模块、§9 里程碑、§10 新增"授权必须落在库里"风险条；功能点清单第 6/11 项同步

## 对标 Higress：链路一（MCP→MCP）工具是否入库
- 结论：**Higress 也是工具不入库**。上游协议 `mcp-sse` / `mcp-streamable`（原生 MCP Server）时只做转发聚合，工具定义在网关内存缓存，持久化的只有连接配置（地址/协议/暴露范围）；配置载体是 CRD + Nacos watcher（不是 DB）
- REST→MCP 那条路（Higress 的 `http/https` 上游）用 `RequestTemplate`/`ResponseTemplate`（`ArgsToJsonBody` / `ArgsToUrlParam` / `PrependBody`）映射——与我们链路二的模板字段几乎同名，印证设计对标正确；差异是 Higress 存配置（K8s 原生/GitOps），我们存 MySQL `mcp_gw_tool`（要支持后台管理与人工修补 `manual_override`、版本灰度）
- Higress 的 Redis 用途 = SSE 会话状态 + 限流，**不是**存工具定义；与我们一致
- 重要发现并已写入方案：**MCP 2026-07-28 已移除 `initialize` / `Mcp-Session-Id`，改为无状态** → §1.2 新增"先确认协议版本再动工"提示（新版本整套会话处理可不做，legacy 后端才需要 Redis 会话外置）；新版协议把 `Mcp-Method` / `Mcp-Name` 放进 HTTP Header，埋点可直接取值但必须与 body 校验一致（不一致 400）；`tools/list` 缓存遵循上游 `ttlMs` / `cacheScope`性与不可伪造：① MCP 面 `/mcp`；② REST 代理面 `/proxy/**`；③ 管理面 `/internal/**`、`/admin/**`、`/actuator/**`（注册心跳、注册表 CRUD、健康检查指标；不对外暴露、不走数据面旁路）。已在 §1 架构图与说明表中写明，并区分"面（入口维度）"与"链路（后端类型维度）"：2.6「多地址」改为「选址」（默认单地址，多地址非核心）、7.3 标题改「治理与容错」、M6 去掉"多地址权重/故障转移"、M7 加入"多地址权重轮询（按需）"、`loadBalancer.pick` → `endpointPicker.pick`、模块描述"负载均衡"→"地址选址"
