## 补齐链路一（原生 MCP）的上游认证 —— 新增 §3.4

用户指出 `mcp_gw_auth_scheme` 只讲了 OpenAPI→MCP 的凭证注入，没讲原生 MCP 路由怎么做。补完后确立的关键结论：

- **装配点不同**：链路二/三按请求模板逐次注入；链路一装配到 **transport 层、连接级复用**（`connect()` 里 `applyUpstreamAuth` + `customizeRequest`）
- **取值降级为一级**：MCP_REMOTE 工具不入库，没有 per-tool 覆盖，只认 `default_upstream_scheme_id`；`api_in=query` 不推荐（凭证进 URL 日志 + SSE GET 与 POST 双通道易漏一处）
- **401 处理**：握手失败即熔断；已建连后 401 → `evict` + 重建 + 只重试一次，单独 `deny_reason=UPSTREAM_AUTH_FAILED` 告警（属配置问题不是抖动）

- 短期令牌（OAuth 2.1）列为按需扩展：需加 `token_url`/`client_id`/`client_secret`/`token_expires_at`，token 缓存到 Redis 供多副本共享

## 重写 §7.1：入口（INBOUND）鉴权讲透

用户反馈「INBOUND 模式下没讲明白怎么做 auth 校验」。原 7.1 只有抽象三步。改后拆成 A（入口）/ B（出口）两节，A 的四步：

1. **取凭证**：`api_in` 的 query/cookie 只允许 OUTBOUND 用；**INBOUND 行必须 `api_in=header`，启动校验违规行拒绝加载**（入口 Key 走 query 会泄进 access log / Referer）
2. **反查**：不能 `WHERE default_credential=?`（打 DB + 密文列无法等值匹配 + 逐行比对的时间侧信道）。改为启动时建「SHA-256(凭证明文) 前 16 字节 → SchemeRow」内存索引，**按值反查**（头名会撞车、值不会）；同 sys_code 可多 Key；**撤销＝从索引摘除，不等 TTL**，30s 轮询兜底
3. **比对**：`MessageDigest.isEqual(sha256(decrypt(cipher)), sha256(presented))`，两边摘要后恒定时间比，禁止 `String.equals`（泄漏长度+首字节位置 → 逐字符爆破）
4. **落上下文**：`X-Sys-Code` 缺省兜底、不一致 401 `SYS_CODE_MISMATCH`；产出 `Caller{sys_code,tenant,user,trace_id,face}`，下游一律只读它

配套补齐：路径保护范围表（`/mcp` 每请求独立鉴权、`/internal/**` 必鉴、prometheus 端点不放行、未匹配路径同样鉴权）；失败码表 `MISSING/INVALID/DISABLED/SYS_CODE_MISMATCH/TOO_MANY_FAILURES` 且**对外不细分「无此 Key」与「值不匹配」**；抗爆破复用 7.2 Redis Lua 按 IP+face 计失败次数；端到端 `tryAuthenticate` 骨架片段
连带同步：§2.2 api_in 字段约束、§7.4-B `auth_failures_total` reason 枚举（去掉 EXPIRED）、§7.4 ② deny_reason=AUTH_FAILED、§7.5 新增入站 `X-Request-Id` 候选值说明、§8 auth 模块职责
取舍记录：**未引入** credential_hash 列 / status 列 / RBAC / 过期时间——复用 `default_credential` 解密比对 + `deleted` 软删即够，避免过度设计

## 补齐全库索引 + `mcp_gw_call_log` 建表语句（用户要求）

五张表现在都有 `CREATE TABLE`（此前 call_log 只有字段表，是我漏了）。每张表配了「索引为什么这样配」的说明表。

- **service**：新增 `UNIQUE uk_route_prefix(route_prefix)`（两个 REST_PROXY 抢同一前缀会让路由不确定；MySQL 唯一索引允许多个 NULL，非 REST_PROXY 留 NULL）；`idx_status` 升级为 `(status, deleted)`；新增 `idx_type(type,status)`、`idx_version`
- **tool**：`idx_service` → `idx_service_status(service_id, enabled, deleted)`；新增 `idx_version`、`idx_updated`
- **auth_scheme**：`idx_dir_sys` → `(direction, sys_code, deleted)`；**保留单列 `idx_sys_code`**（复合键最左前缀不匹配"只按 sys_code 查"，不算冗余）；新增 `idx_version`；**明确不给 `default_credential` 建索引**（密文列、比对走内存 SHA-256 反查，建索引等于在索引里留 Key 前缀）
- **grant**：删掉冗余的 `idx_sys`（已被 `uk_grant(sys_code, service_id)` 最左前缀覆盖）；新增 `idx_service`（反向查"服务授权给谁"+ 删服务级联）、`idx_version`、`idx_expire(status, expire_at)`
- **call_log**：`PRIMARY KEY (id, created_at)` —— **MySQL 分区表硬性要求每个唯一键都包含分区列**，否则按月分区直接报错；`PARTITION BY RANGE (TO_DAYS(created_at))` + pmax 兜底；索引 `idx_trace` / `idx_sys_time` / `idx_service_time` / `idx_status_time`；清历史用 **DROP PARTITION 而非 DELETE**；不建索引：`args_digest`、`tool_name`、`face`/`route`/`tenant`
- 新增「**索引设计原则（五张表通用）**」5 条：每个索引要能说出服务哪条 SQL；四张注册表统一 `idx_version`（它们都几百到几千行，真正吃索引压力的只有 call_log）；低区分度列不单列建；列名≠要建索引；索引替代不了外键（唯一性靠 uk_*，一致性靠 2.7 软删+校验）

写进 §2.3 开头的一段结论：**它是原始名（raw name，= OpenAPI operationId，缺失/重复时 method+path 兜底），不是关联键**。三重身份：

1. **对外工具名的后半段**：`tools/list` 返回 `{service.name}.{tool_name}`；MCP 协议的 `name` 必须是模型能认的字符串，不能是自增 id，前缀解决跨服务重名
2. **调用时的查表键**：`tools/call` 的 `order.createOrder` → resolver 拆出 service + rawTool → 按 `uk_service_tool(service_id, tool_name)` 取 `request_template`；**路由全程不需要工具 id**
3. **授权名单元素**：两处 `allow_tools` 存原始名字符串

- 关键补充结论两条：
- **改 tool_name 是破坏性操作**（对外契约：Agent 系统提示/历史上下文 + 两处名单都固化这个字符串）。原地 rename → 工具从名单掉出变成不可调用（fail-closed，安全方向对但表现为突然不可用）。正确姿势：新增新名 → 两处名单补新名 → 灰度 → 下线旧名
- **`allow_tools` 为什么存名字不存 tool_id**（补在 §2.6 规则 3 后）：它不是表间引用而是协议层字符串契约；MCP_REMOTE 工具不入库根本没有 id，服务 allow_tools 却必须能限制这类服务；按名字写才与请求侧对齐。代价是名字与名单的一致性由人保证

## 新增 §7.1-C「凭证的存储与取回」（用户提问：AES-GCM 加密后怎么看原始数据）

原文档只写了"凭证 AES-GCM 加密存储"，没写运维要看到明文时怎么办，这是设计缺口。补齐的判断链：

- **核心定性**：AES-GCM 里 IV 与 tag 就在那一列里，唯一不在库里的是 KEK。所以「能不能看明文」等价于「能不能碰到主密钥」，与算法难度无关；没有 KEK 改动任一 bit 都抛 `AEADBadTagException`，无旁路。**"看不到原始数据"是加密的交付物而非副作用**
- **C-3 三种诉求只有一种真要明文**：确认某把 Key → 不用解，用 Key 指纹比对；作废/换凭证 → 不用解，覆盖写；**后端凭证原值丢失需去第三方平台核对 → 才走受控取回**
- **取回通道二选一**：首选**离线 CLI**（堡垒机跑，产品里不存在"吐后端密码"的 HTTP 端点）；次选管理面 `reveal`，要求独立权限点 `credential:reveal`、强制 reason + 二次确认、**响应明文排除在 access log / L1 / L2 之外**、独立不可删审计流水、批量 reveal 告警
- **C-5 实现三条易错点**：① IV 每次随机使同明文两次密文不同，故**不能靠密文相等判断两行凭证相同**（要判重另存明文哈希，也只做 true/false 比对）；② **AAD 必须绑定 `schemeId + direction`**，否则整段密文可被复制到高权限行造成串权，但放进去的字段必须终身不变；③ KEK 不入同一库/配置/Git，禁止为测试留 skip-decrypt 开关
- **C-6 KEK 滚动**：密文加版本前缀（`v1:`）以便新旧 KEK 并存过渡；无前缀则只能停机一次性切换
- **新增硬约束落 §7.4②**：凭证原文在 access log / L1 / L2 三种载体里都不出现，"新增打印全部请求头的诊断开关之前先确认它是否会碰到凭证"；加密列不是唯一防线，日志是最容易把收敛打散的地方
- 连带同步：§1 选型表、§2.2 字段表 + DDL comment、§7.1-B 末条、`MCP网关功能点清单.md` 第 5 项

## 澄清 `endpoints[].status = DRAIN`（用户提问）+ 修复一处真实缺陷

原文档三处只写了「`DRAIN` 元素不接新请求，用于优雅下线」，且 §3.4 的 `evict(url)` 注释是"下线 / 摘流 / 熔断时调用"——**把三种性质不同的操作合并了**，导致计划内发布会直接 `pool.remove + close` 杀掉在途请求，优雅下线形同失效。

定性：`OFFLINE` = 系统判定"它坏了"（心跳超 90s / fail_count 阈值），立即止损 + 半开探活自动恢复；`DRAIN` = 人工标记"它要走了"，**不接新请求但放行在途直到归零才关**，且**永不自动恢复**（探活成功也不能拉回候选名单，否则滚动发布期间会被自动塞回）。两者区别是性质不是程度。

改动：
- **§2.1** 新增「`endpoints[].status` 三态」对照表 + 两段说明：① 为何两者不能共用同一套实现；② **K8s 已有优雅下线为何网关仍需这一层**——摘 endpoint 到 SIGTERM 之间有窗口，且链路一在网关侧持有长连接与复用 transport，K8s 摘不动。**DRAIN 不是容错机制，是发布流程的一环**
- **§2.7 选址**：DRAIN 与 OFFLINE 都不入候选；**全部元素不可选时返回 503 + `Retry-After`**，而不是挂在待关闭连接上超时
- **§3.4 连接池**：`evict()` 收窄注释为 OFFLINE/熔断专用；**新增 `drain(url)`** = `awaitIdle(url, 30s).thenRun(() -> evict(url))`，配套要求里加「必须带兜底超时，宁可放弃优雅也不能卡死发布（记 `DRAIN_TIMEOUT`）」与「`healthCheck` 只管 OFFLINE 一路」
- **§5（地址级容错）**同条改写，指向 2.1 / 3.4

### 二次纠正：下线 ≠ 删数据，是分层的（用户问"下线不是 status 设 DISABLED？"）

1. **停用一个服务（最常用）= `mcp_gw_service.status = DISABLED`**，工具/授权/地址全保留，可原地恢复

4. 彻底废弃 = 软删 `deleted=1` + 连带处理工具与授权

## 限流配额单位改为 QPM（用户指出：INT 存不了小数，且实践用 QPM 更多）

- **列改名**：`mcp_gw_service.qps_limit` / `mcp_gw_auth_scheme.qps_limit` → **`qpm_limit` INT，单位「次/分钟」**（字段表 + DDL comment 同步）
- **理由（写入 §7.2 新小节「配额单位：全系统统一 QPM」）**：INT 列存"每分钟 30 次"用 QPS 只能写 `0.5`（存不下）或被拍成 `1`（放大一倍）；工具调用低频突发，`30` 比 `0.5` 可读；第三方开放平台额度表也多用 QPM/QPD
- **只留一个单位，不加 `rate_unit` 列**：加单位列会让快照构建 / Lua / 管理面展示 / 校验告警全部要分支——与 `endpoints[].status` 加第三态是同一种"一处灵活、N 处复杂"的成本；QPS↔QPM 只是 ×60 心算，文档括注等效 QPS 即可。**精度下限 1 次/分钟**，更低频不支持
- **`burst` 缺省语义必须跟着改**：原"取 `qps_limit`"会让突发容量放大 60 倍（600 QPM 却允许 600 次突发）→ 改为 **`ceil(qpm_limit/60)`，最小 1**
- **Lua 令牌桶改为浮点 tokens**（新增完整脚本 + 4 条注意）：QPM 下每秒补充量几乎必为小数，**绝不能对补充量取整**——`floor(elapsed*qpm/60000)` 且每次把 `ts` 推进到 now，会造成"补充量恒为 0 → 桶永不回补 → 突发耗尽后永久 429"的死锁；正解是余数留在 `tokens` 里累加，只在取令牌时做整数比较。`Retry-After = max(1, ceil(retry_ms/1000))`；冷桶 TTL 必须 ≥ `burst/qpm` 分钟否则等于重置成满桶；Redis 5+ 用脚本内 `TIME` 取服务端时间，早期版本需 NTP 对齐由客户端传 now_ms
- 环境变量同步：`mcp.gw.ratelimit.global-qps/-unknown-qps` → `global-qpm` / `unknown-qpm`（unknown 默认 **300 QPM**，沿用原 5 QPS 口径）
- 连带同步：§2.2 示例（`AGNT=3000` / `CRMWEB=1200`，括注等效 QPS）、§7.2 配置表与三档示例、§9 M5、`MCP网关功能点清单.md` 第 4 项

## 用户追问："为什么不直接用小数？"——采纳，改为 DECIMAL(10,4)

- **承认上一轮的错误**：把「有几个单位」与「数值能不能是小数」两个正交决定捆在一起了。反对多单位（不加 `rate_unit` 列）成立；但顺手否掉小数是错的——**小数不引入任何单位分支，只是让同一单位覆盖更宽量程**
- **最终口径**：单位统一「次/分钟」+ 类型 **`DECIMAL(10,4)`，允许小数**。量程覆盖：2000 QPM(≈33 QPS) / 30 / 0.1667(10 次每小时) / 0.0694(100 次每天) / 0.0010(10 次每周) —— 四个数量级，一个单位全包。**这才是"兼顾 QPS/QPH/QPD"的方式：靠精度，不靠多单位**
- **可读性的正解在输入层不在数据层**：管理面做成"数值 + 单位下拉(QPS/QPM/QPH/QPD)"，提交前换算成 QPM 落库、展示时反向渲染。这与被否掉的 `rate_unit` 列的区别 → **那是把单位写进数据模型**（快照/Lua/告警/展示每处都要分支），**这是单位只活在表单的一个换算函数里**（网关/Redis/Lua/快照永远只见一个数字一种单位）。一处换算，N 处干净。**禁止裸数字输入框**（错误双向：50 QPS 填成 50 → 变 0.83 QPS；0.83 QPS 填成 3000 → 放大 60 倍，数值表面都看不出来）
- **必须 DECIMAL 而非 FLOAT/DOUBLE**：定点精确，`0.1667` 存读严格相等；配额要被机器比对（同 sys_code 多行一致性告警）也要被人工核对，不容忍二进制浮点误差。Java 侧两条纪律：**用 BigDecimal 读取比对，禁止先转 double 再比较**（0.1 转 double 就不等 → 告警天天误报）；**BigDecimal→double 只允许在传参给 Lua 的那一次**
- **精度下限**：`DECIMAL(10,4)` 最低有效值 `0.0001 QPM`（≈每天 0.14 次）；落库校验 `qpm_limit > 0`，小于 `0.0001` 拒绝保存（那是配错单位）
- **低速率的两条连带结论**：① `burst` 在 `qpm_limit < 60` 时必然取 1，**这是对的**（每小时 10 次不该有"攒着一次打完"的额度）；② `Retry-After` 如实返回不截断（10 次/小时 → `Retry-After: 360`，截断会让客户端更早重试反而放大压力），但对**单次等待 > 60s 的拒绝单独告警**——持续撞低频配额说明上游没做本地节流
- `burst` 保持 **INT**（令牌个数天然整数）；§2.1/§2.2 字段表 + DDL comment 同步；§2.2 示例加一行 `BATCHJOB qpm_limit=0.1667` 演示小数配额
