## JSON 字段是否该改成独立表（用户提问，暂未改动设计文件）

用户质疑"所有 JSON 字段不适合关系数据库，不好做分析和排查"。盘点出全库 **13 个 JSON/TEXT 字段**，分四类给出结论——**只建议拆 1 个**：

| 类别 | 字段 | 结论 |
| --- | --- | --- |
| 标量数组（深度 1） | `passthrough_headers` / `include_tags` / `allow_tools`(service) / `allow_tools`(grant) | 只拆 `grant.allow_tools` |
| 对象数组（深度 1，元素有身份） | `endpoints[{url,weight}]` | 维持 JSON（触发条件已有：地址数>20 或需单地址审计） |
| 嵌套文档（深度≥2，整体消费） | `input_schema` / `request_template` / `response_template` / `output_schema` | 不拆 |
| 外部副本 / 归档快照 | `spec_json`(MEDIUMTEXT) / `error_response_template` / `args_digest` | 不拆 |

**核心论证（可复用）**

1. **热路径零收益**：注册表是"读多写少、整体进内存"（§2.7），`tools/call` 取一行反序列化成对象常驻内存。存成 JSON 还是 5 张子表，进内存后是同一个对象——拆表只改持久化形态，热路径不变，持久化凭空多出组装逻辑。
2. **冲击 version 增量刷新**：拆成父子表后"改一个入参涨谁的 version"无解，各 Pod 组装结果不一致。
3. **跨元素约束退化**：`argsToJsonBody` 与 `body` 互斥这类约束，JSON 里是加载时一次校验，拆表后只能退到应用层。
4. **EAV 才是公认反模式**：把 `config_json` 拆成 `(id,key,value)` 是用 JSON 的 1 个缺点换 EAV 的 3 个缺点（无类型 / 无嵌套 / 自 JOIN 再 PIVOT）。
5. **MySQL 的 JSON 不是 TEXT**：JSON 是二进制格式，支持路径查询 / 部分更新 / 函数索引 / 多值索引；"不适合关系数据库"对 TEXT 成立，对 JSON 不成立。
6. **`grant.allow_tools` 是唯一的例外**：它是授权主体 = 安全审计的直接对象，需要行级粒度；而且拆出来后工具改名产生的孤儿字符串不再被 JOIN 伪装成正常数据。

**用户痛点的真正解法（不拆表）**：① 缺索引 → MySQL 8 多值索引 `CREATE INDEX idx_pt ON mcp_gw_service((CAST(passthrough_headers AS CHAR(64) ARRAY)))`，配 `MEMBER OF` 走索引；② 缺变更审计 → 新增 `mcp_gw_config_audit(target_type,target_id,field,before_json,after_json,operator,created_at)`；③ 缺关系化视图 → `JSON_TABLE` 建视图供排查时用。**审计跟存储格式正交：拆成 EAV 也不会自动产生审计。**

**待用户拍板后才动**：① 拆出 `mcp_gw_grant_tool(grant_id, tool_name)`；② 加 `mcp_gw_config_audit`；③ §2 补一节"JSON 列的检索与排查"。

### 技术选型收敛与凭证存储简化（commit `ed773c3` 技术选型 / `413ecd4` 冷却期 / `a8c5440` 凭证明文）

**1) JDK 与阻塞隔离**
- 语言行 → **Java 25 LTS + Spring Boot 3.x（`--release 21` 编译）**：编译目标锁 21 → 运行时给 25 跑 25、内网只批 21 就跑 21，切换零改动；误用 22+ API 编译期即报错，**版本决策推迟到部署时刻且可逆**
- 选 25 的真实理由（不只是新）：JDK 24 起 JEP 491 修复了虚拟线程在 `synchronized` 块内阻塞 pin 住载体线程的问题；21 上需 `-Djdk.tracePinnedThreads=full` 观测
- 隔离行去掉"或"→ **虚拟线程 + 信号量舱壁**（缺一不可：虚拟线程近乎零成本，没有舱壁等于没有隔离）；全文"独立线程池"旧提法已对齐（含 M2 里程碑、§3.2 注释、§10）

**2) 熔断冷却期 30s → 5s**（§2.1 / §2.7 / §3.2 `COOLDOWN_MS` 三处同步）
- 理由：半开借业务流量，冷却结束后最多每 5s 才被打一发，不存在试探放大；30s 意味着后端恢复后平均要等 15s
- 阈值与冷却期**一期写死、不提供按服务配置**（原"可配置"是空承诺，与其留着不如写死）

**3) `strip_prefix` 是否改成动态 N（未改，用户说先不动）**
- 关键论证：**"/proxy/{prefix}/**" 的 path variable 不跨斜杠** → route_prefix 天然只能是单段，"剥几段"恒等于 2，所以布尔就够
- 多段前缀（`/biz/order`）的代价列表：需改 `/proxy/**` + 最长前缀匹配（O(1)→O(n)）、uk 唯一不够还要防互为前缀、排查变难；**收益为零**（分组语义已由 `service.name` 提供，工具名 `order-svc.xxx`）
- 结论给到用户：**动态 N 与多段路由是两个独立的事，可以只做 A（剥 N 段，用于后端自带 context path）不做 B（多段路由）**

**5) 缓存去掉跨副本广播（commit `d1e6b3a`）**
- 用户问"缓存存在跨副本变更吗" → 结论：**不存在**。三类缓存写入方：注册表快照/授权/凭证索引 = MySQL 只读投影（本地不写）；熔断计数与连接池 = 刻意 Pod 私有；MCP 工具列表 = 本 Pod 与后端之间。没有"A 改了通知 B 作废"的场景
